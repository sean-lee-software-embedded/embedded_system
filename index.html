1.1 / EMBEDDED SYSTEM

什麼是Yocto Build System？

Yocto Project提供建立客製化Embedded Linux系統的工具、Metadata與開發方法。一般所說的「Yocto Build」，通常指透過BitBake與OpenEmbedded Metadata，建置Toolchain、套件、Kernel及Image的流程。

它不是一份固定內容的Linux發行版，也不只是一個Compiler。你用Metadata描述要取得哪些Source、套用哪些Patch、如何Configure／Compile／Install，以及最終Image包含哪些套件。

組成用途
BitBake解析Metadata、處理Task Dependency與執行Build Tasks。
OpenEmbedded-Core提供共用Recipes、Classes與核心Metadata。
PokyYocto Project的Reference Distribution／整合範例。
Machine／Distro設定選擇目標硬體與發行版政策。
sstate／Downloads重用可用的Task輸出與Source下載，減少重複工作。
理解依賴順序即可先入門：取得Source、套Patch、Configure、Compile、Install到暫存目錄、產生Package，再組成Root Filesystem與Image。實際Task由Recipe與繼承的Class決定。
# 在已初始化的專案Build環境執行；名稱皆為範例
bitbake exampled
bitbake core-image-minimal
bitbake-layers show-layers
bitbake-layers show-recipes exampled

請先使用專案規定的Environment Setup與MACHINE設定。OpenBMC等專案可能有自己的Setup Script與Image名稱；不必另建一套Poky來修改既有專案。

參考：Yocto Project Concepts

1.2 / EMBEDDED SYSTEM

什麼是Recipe、Layer與Image？

名詞定義例子
Recipe通常以.bb描述一個軟體元件如何取得、建置、安裝及產生套件。exampled_1.0.bb
Layer一組有組織的Metadata，包含Recipes、設定及Classes等，可依功能／硬體／產品分層。meta-company
Image描述最終Root Filesystem內容及相關輸出；Image Recipe指定要納入的Packages與Features。core-image-minimal
bbappend擴充或修改既有Recipe的Metadata，不需直接修改上游.bb。exampled_%.bbappend

Recipe常見欄位

欄位／Task用途
SRC_URI／SRCREVSource與Patch來源，以及Git等來源的Revision。
LICENSE／LIC_FILES_CHKSUMLicense聲明與來源License內容的檢查資訊。
DEPENDSBuild-time Recipe依賴。
RDEPENDS:${PN}某個輸出Package的Runtime依賴。
do_install將檔案安裝到Recipe的暫存目的目錄${D}。
FILES:${PN}指定哪些已安裝檔案屬於該Package。
IMAGE_INSTALLImage要安裝哪些Package；不是任意Recipe都能直接當Package名稱。
一個Recipe可能產生多個Packages，例如主程式、Library與Debug Symbols。編譯成功不代表檔案已被Package收錄，也不代表Package已進入最終Image。

Debug順序：先確認Recipe實際被選到，再檢查do_install輸出、Package內容與Image安裝清單；遇到問題不必一開始就清掉整個Build Cache。

1.3 / EMBEDDED SYSTEM

什麼是devtool？modify、build與deploy怎麼用？

devtool協助在Yocto Build環境或eSDK中修改既有Recipe的Source、建置及測試，並將修改整理回正式Layer。

指令做什麼要留意什麼
devtool modify exampled取出Recipe Source、套用既有Patch，建立或使用開發用Source Tree與Workspace設定。它改變的是開發來源的使用方式；不會自動完成正式Patch整合。
devtool build exampled依Recipe及Workspace Source執行建置所需Task。不是每次重建整份Image，也不是直接把程式送到Target。
devtool deploy-target exampled user@target將do_install產出的檔案部署到可SSH連線的Target。常用子命令名稱是deploy-target；不是devtool deploy。
devtool undeploy-target exampled user@target撤回這次Development Deployment。不是整機Snapshot，仍須確認Target狀態。
devtool finish exampled /path/to/layer將已Commit的修改整理到指定Layer，並結束Workspace修改狀態。先確認Git Commit及輸出Patch，再驗證正式Build。
# Build Host：先進入專案已初始化的Build環境
devtool modify exampled
devtool status

# 到devtool顯示的Source目錄修改程式，再回Build目錄執行
devtool build exampled

# 部署前先依下一節停止受影響Service
devtool deploy-target exampled root@bmc.example.com
deploy-target會繞過Target的Package Manager，也不會自動部署所有Runtime Dependencies。Target需有相容Library、可寫入的路徑及足夠權限；它適合開發驗證，正式交付仍應整合Layer並重新產生Package／Image。

參考：Yocto 5.1 devtool Quick Reference

1.4 / EMBEDDED SYSTEM

systemd、start／enable與新Daemon快速驗證

systemd是Linux常見的System與Service Manager，通常作為PID 1運作，以Unit管理Service、Socket、Timer及Dependency等。systemctl是操作它的工具。

正確指令順序是systemctl start SERVICE

指令立即影響之後是否自動啟動
systemctl start exampled.service現在啟動Service。不會因此建立開機啟用設定。
systemctl enable exampled.service依[Install]建立啟用連結；單獨使用通常不會立即啟動。在對應Target／啟動條件到達時可被啟動。
systemctl enable --now exampled.service啟用並立即啟動。依Unit啟用規則運作。
systemctl restart exampled.service停止後重新啟動。不改變Enable狀態。
systemctl daemon-reload重新讀取Unit設定與Dependency。不會自行Restart既有Process。
systemctl reload exampled.service要求Daemon重新載入自身設定；需Service支援。不同於daemon-reload。

Static Unit可能沒有[Install]，但仍可由Dependency或Socket／D-Bus Activation啟動。enabled不代表目前active；disabled也不代表不可能被其他Unit拉起。

Build完新的System Daemon，如何快速驗證？

範例Recipe／Service／Binary均使用exampled；實際名稱可能不同。先確認Service影響範圍，再在開發Target進行以下操作。

# Terminal A，Build Host：先停止Target上的舊Process
TARGET='root@bmc.example.com'
ssh "$TARGET" 'systemctl stop exampled.service'

# 在已完成devtool build的環境部署新檔案
devtool deploy-target exampled "$TARGET"
# Terminal B，Target：若新增或修改Unit，先重新讀取
systemctl daemon-reload
systemctl start exampled.service
systemctl status exampled.service --no-pager
journalctl -u exampled.service -b -n 100 --no-pager
systemctl show exampled.service -p MainPID -p ExecStart -p User
sha256sum /usr/bin/exampled
  1. 確認正在跑的是新Binary、正確ExecStart與設定；不能只確認檔案已Copy。
  2. 觸發一個可觀察的真實功能，例如D-Bus Method、資料更新或API查詢，核對結果與Log。
  3. 檢查Restart／Crash、CPU與Memory，並在結束後撤回臨時部署或整合正式Image。

若直接執行Binary可成功，但透過systemd失敗，對照User、Environment、WorkingDirectory、Dependency及Sandbox設定。需要Foreground Debug時先停原Service，避免爭用D-Bus Name、Port或硬體。

參考：systemctl Manual；Yocto 5.1 devtool Quick Reference

1.5 / EMBEDDED SYSTEM

Git基本開發流程

基本路徑是：同步Remote資訊、建立工作Branch、修改、Review Diff、Commit、測試、Push，再建立MR／PR。以下假設Repo已有origin/main；實際主線名稱依專案調整。

git status
git fetch origin
git switch -c feature/exampled-log origin/main

# 修改Source後，檢查及選擇要提交的檔案
git diff
git add src/exampled.cpp
git diff --cached
git commit -m "Fix exampled error logging"

# 執行與修改相關的Build及測試後
git log --oneline -5
git push -u origin feature/exampled-log
Working Tree是目前檔案；Staging Area是下次Commit要收錄的內容；Commit是版本紀錄。fetch更新Remote Tracking資訊，不會自動把工作Branch合併到最新版。

先確認status與Diff，避免把Build產物、密碼或無關修改放入Commit。送Review時交代問題、修改後行為與驗證方式。

1.6 / EMBEDDED SYSTEM

git rebase、git merge與git cherry-pick

Rebase與Merge的差異

面向MergeRebase
作用整合另一條Branch的歷史。將目前Branch的Commits重新套用到新的Base。
Commit ID原有Commit保持；非Fast-forward整合通常產生Merge Commit。被重新套用的Commit通常產生新ID；歷史會改寫。
歷史形狀保留分支與整合關係；Fast-forward可能只移動Branch Pointer。通常整理成較線性的歷史。
常見用途整合共用Branch，保留協作歷史。整理尚未共享的個人Branch，跟上最新主線。
# 先確保Working Tree乾淨；以下兩種方式擇一
# A：在目前工作Branch合併最新主線
git fetch origin
git merge origin/main

# B：在目前工作Branch重新套用到最新主線
git rebase origin/main

遇到Conflict時，讀懂兩邊意圖、修改檔案、git add後使用對應的--continue；想回到操作前可用該操作的--abort。整合後重新Build與測試。不要任意Rebase他人正在使用的共用歷史。

Cherry-pick：挑選特定修正

git cherry-pick把指定Commit引入的變更套到目前Branch，通常產生新Commit。適合將一個Fix移植到Release Branch；不是直接合併整條來源Branch。

# 假設已在正確的目的Branch；先看實際Commit內容
git show abc1234
git cherry-pick -x abc1234

# 若發生Conflict：修正檔案、git add之後
git cherry-pick --continue

# 若決定取消此次Cherry-pick，改用：
# git cherry-pick --abort

abc1234是範例，請替換成真實Commit。-x留下來源Commit資訊。即使套用沒有Conflict，仍可能缺少前置修正或不符合舊Branch API，必須重新驗證。

參考：git-merge、git-rebase與git-cherry-pick

1.7 / EMBEDDED SYSTEM

怎麼看CPU Usage與Memory使用量？

# Target：觀察整體狀態
top
free -h
cat /proc/meminfo

# 以下適用procps工具；PID請替換成實際Process ID
PID=1234
top -H -p "$PID"
ps -p "$PID" -o pid,ppid,comm,%cpu,%mem,rss,vsz
cat "/proc/$PID/status"

# Kernel及權限允許時，查看較完整的Process Memory統計
cat "/proc/$PID/smaps_rollup"
觀察值如何判讀
CPU %看採樣期間、Thread與CPU數量；多Thread Process在常見顯示模式下可能超過100%。ps的%CPU通常反映執行期間平均，與top即時採樣不同。
Load Average反映Runnable與部分Uninterruptible工作負載；不是CPU百分比。
RSS／VSZRSS是Resident Memory；VSZ是Virtual Address Space大小，不能直接當作實際RAM使用量。
PSS依共享比例分攤Memory，有助比較共享Library較多的Process；需Kernel支援。
MemAvailable／Cache可用Memory要考慮可回收Cache；free很少不等於發生Memory Leak。
時間趨勢固定操作條件，反覆觸發並比較；單次數字不能證明Leak。

Embedded Image可能只有BusyBox，選項與GNU／procps版本不同。先看--help；缺少完整工具時可讀/proc，或在開發Image加入所需診斷套件。

參考：top、free與Linux /proc文件

怎麼檢查Service與Port？

# Target：Process與Unit不等於同一件事
systemctl status exampled.service --no-pager
systemctl is-active exampled.service
systemctl is-enabled exampled.service
journalctl -u exampled.service -b -n 100 --no-pager
systemctl list-units --type=socket --all

# TCP Listener與UDP Socket；顯示Process資訊通常需要較高權限
ss -lntp
ss -lunp

# 本機確認HTTPS服務；需替換成相符的Hostname與CA
curl --cacert /path/to/bmc-ca.pem -i https://bmc.example.com/redfish/v1/
  1. 先確認Service是否啟動、是否反覆Restart，並讀取Log。
  2. 確認是否真的Listen、綁定哪個Address／Port，以及擁有Socket的Process。
  3. 本機可用但遠端不通時，檢查路由、Firewall、Bind Address與Network Namespace。
  4. TCP可連線但API失敗時，再檢查TLS、Authentication及Application回應。
Service可以只提供D-Bus介面，完全沒有TCP／UDP Port。Socket Activation也可能先由systemd持有Listener；不能只用Process名稱判斷Port是否存在。UDP沒有TCP式的Listen Handshake。

1.9 / EMBEDDED SYSTEM

什麼是GDB？基本使用情境

GDB（GNU Debugger）可以在程式執行時設Breakpoint、單步執行、讀取變數與Call Stack，也能分析Core Dump。常見情境是Crash、卡住、邏輯走錯路徑及多Thread問題。

先準備與實際Binary匹配的Debug Symbols；-g產生除錯資訊，最佳化會影響變數與單步觀察。開發時可視建置政策使用-Og；不要假設Release Binary一定保留Symbols。

# 在支援該程式架構、且具備Symbols的環境
# A：啟動程式除錯
gdb --args ./exampled --config ./example.conf

# B：Attach既有Process；PID為範例，擇一使用
# gdb -p 1234

# C：分析與Binary同一Build的Core Dump
# gdb ./exampled ./core.exampled
# GDB Prompt內的常用指令
break main
run
next
step
print variable_name
bt
info threads
thread apply all bt
continue

# Attach情境結束時可detach，讓Process繼續執行
# detach

Embedded常用：Host GDB＋Target gdbserver

# Target：PID為範例；只在受控Debug網路開放此Port
gdbserver --attach :2345 1234

# Build Host：使用支援Target架構的SDK GDB或gdb-multiarch
# 載入同一Build、未Strip的Binary
# 以下是在GDB Prompt內：
file /path/to/unstripped/exampled
set sysroot /path/to/target-sysroot
target remote bmc.example.com:2345
thread apply all bt
continue
Attach／Breakpoint通常會暫停Process，可能觸發Watchdog、Timeout或改變時序。使用對應Binary、Library、Architecture與Symbols；不要把Host Library誤當Target Library。gdbserver本身不提供完整Authentication保護。

Crash先看bt及各Thread；Hang先看Thread是否等Lock、I/O或Event。看到某行Code不等於已找到Root Cause，還需結合Log、輸入條件與可重現實驗。

參考：GDB Manual

1.10 / EMBEDDED SYSTEM

什麼是DTS、DTC與DTB？怎麼Debug？

Device Tree描述硬體拓樸與參數，讓Kernel知道有哪些裝置及如何匹配Driver。它不是Driver程式碼。

名詞用途
DTSDevice Tree Source，可閱讀的硬體描述檔，副檔名.dts。
DTSI共用Include片段，常描述SoC或共用Board資訊。
DTCDevice Tree Compiler，將Source與Binary格式互相轉換的工具。
DTBDevice Tree Blob，編譯後的Binary，通常由Boot Firmware傳給Kernel。
# Build Host：獨立且不需C Preprocessor的簡單DTS範例
dtc -I dts -O dtb -o board.dtb board.dts

# 反編譯既有DTB，以便比對
dtc -I dtb -O dts -o decoded.dts board.dtb

# Target：若有dtc，查看Kernel實際使用的Live Device Tree
dtc -I fs -O dts -o running.dts /sys/firmware/devicetree/base

# 查看Boot與Driver Probe相關訊息
dmesg
cat /sys/kernel/debug/devices_deferred

最後一項需Kernel提供相關Debug資訊並掛載debugfs。Linux Kernel DTS常使用#include、Macro與專案Build規則，不能一律直接丟給dtc；應優先使用Kernel／Yocto的正式DTB建置流程。

裝置沒有出現時，怎麼查？

  1. 先核對Bootloader載入的DTB及Live Device Tree，確認修改真的進到執行中的系統。
  2. 檢查Node的status、compatible及Parent Bus；再核對Driver是否有編入／載入。
  3. 依Binding核對reg、interrupts、clocks、resets、pinctrl與供電等Property。
  4. 看Probe Log與Deferred Probe，區分缺少Dependency或Hardware未回應。
  5. 比對Binding與Schematic；能跑dtc不代表符合所有Binding或硬體接線。
反編譯DTB通常無法還原原始Include結構、註解與所有Label。若修改DTS但行為沒變，第一步應確認載入的是哪份DTB，而非直接再改Driver。

參考：Linux Devicetree Usage Model；Devicetree Specification

1.11 / EMBEDDED SYSTEM

Toolchain、Cross-compilation與常見問題

Toolchain是一組開發工具，包含Compiler、Assembler、Linker、Binary Utilities及相關Runtime／Header等配套；SDK通常還提供Sysroot與環境設定。

Cross-compilation是在Build Machine上產生給另一個執行環境使用的Binary，例如在x86-64 Linux建置ARM BMC程式。Sysroot提供目標環境的Headers與Libraries，避免混入Build Host的檔案。

情境機器角色
一般Application Cross-buildBuild是執行Compiler的機器；Autotools的Host是產出程式預計執行的機器。
建置Compiler等工具Target可能另外表示該Compiler要產生哪個平台的程式。不要把所有語境的host／target當成同一定義。
# Build Host：source專案產生、與Target Image匹配的SDK環境
# 檔名為範例，請使用實際安裝路徑
. /opt/sdk/environment-setup-armv7a-poky-linux-gnueabi

# Yocto SDK的CC可能包含必要Flags，依SDK指引使用
$CC $CFLAGS --sysroot="$SDKTARGETSYSROOT" hello.c -o hello $LDFLAGS
file hello
readelf -h hello
readelf -l hello
readelf -d hello
症狀常見原因調查與處理
Exec format error用了Host Compiler、Architecture或ABI不符。檢查file／readelf與SDK環境，使用正確Compiler並重建。
檔案存在卻No such file or directory可能缺少ELF Interpreter，也可能是Script的Shebang問題。用readelf -l看Interpreter，核對Target路徑。
找不到.so／GLIBC或GLIBCXX版本不符Target Runtime與SDK／Library不匹配。核對NEEDED、Loader與Library版本；用匹配Sysroot重建，勿隨意覆蓋系統libc。
找不到Header或Library缺Build Dependency、Sysroot或pkg-config路徑錯誤。補Recipe DEPENDS；確認Build工具使用Target Sysroot，避免抓Host Library。
undefined referenceLink Library、順序、ABI、C／C++ Symbol等有問題。檢查Link Command與Symbols；使用匹配Toolchain及Dependency。
Configure測試程式無法執行Build流程想直接執行Target Binary。使用Build System的Cross設定、適當Cache或受支援Emulator；不能直接當Host程式跑。

1.12 / EMBEDDED SYSTEM

什麼是D-Bus？Method／Signal差異與Debug

D-Bus是常用於Linux的IPC機制，讓Process以明確的Object與Interface交換Message。System Bus通常服務系統Daemon；Session／User Bus則用於使用者環境。OpenBMC常以System Bus連接管理Service。

元素代表什麼範例
Bus NameService在Bus上的名稱。org.freedesktop.systemd1
Object PathService內某個物件的位置。/org/freedesktop/systemd1
Interface某組Method、Property與Signal的約定。org.freedesktop.systemd1.Manager
MemberInterface中的Method或Signal名稱。ListUnits
Signature參數與回傳值的型別編碼。s是string，b是boolean，u是uint32；a表示array。

D-Bus Method與Signal有什麼不同？

面向MethodSignal
用途向特定Service／Object提出請求。通知狀態改變或事件。
回應通常收到Method Return或Error；可有不要求回覆的呼叫。沒有Method式的Return／Error回覆。
傳遞模式有明確目的地與方法名稱。常讓符合Match Rule的訂閱者接收，也可指定目的地。
例子呼叫ListUnits取得Unit清單。PropertiesChanged通知Property變更。

D-Bus Property透過org.freedesktop.DBus.Properties的Get／Set等Method存取；變更通知常使用PropertiesChanged。不是每個Property都保證發出相同通知，要看Interface定義與Annotation。

Debug順序：先探索，再讀取／呼叫，最後監看事件

# Target：以下使用常見的systemd介面，先探索實際內容
busctl --system list
busctl --system tree org.freedesktop.systemd1
busctl --system introspect org.freedesktop.systemd1   /org/freedesktop/systemd1

# 讀取Property；需平台提供此Property
busctl --system get-property org.freedesktop.systemd1   /org/freedesktop/systemd1   org.freedesktop.systemd1.Manager Version

# Read-only Method範例，無輸入參數所以不需額外Signature
busctl --system call org.freedesktop.systemd1   /org/freedesktop/systemd1   org.freedesktop.systemd1.Manager ListUnits

# 另一個Terminal監看Service訊息，以Ctrl+C結束
busctl --system monitor org.freedesktop.systemd1
  1. 確認連到System或User Bus，以及目標Bus Name目前是否有人持有。
  2. 核對Object Path、Interface、Member與Signature；不要只根據Source裡的名稱猜測。
  3. 先Introspect，再Get或Call，保存Error Name與Message。
  4. 觀察Signal時先啟動Monitor，再觸發事件；Signal通常不會替晚到的Client保存歷史，必要時先Get目前狀態。
  5. 查Service Log、Access Policy與Process Event Loop；Timeout可能是Handler卡住，不只代表Bus不通。
systemd Unit名稱與D-Bus Bus Name是不同識別方式；可由busctl status查Owner Process，再對照systemctl及journal。Method Call完成只代表API呼叫完成；若設計為非同步工作，仍須依介面約定追蹤後續狀態。
整合練習：新的Daemon看起來沒作用

先確認部署的Binary與正在跑的PID，再看Unit／Journal；確認D-Bus Name與Object是否存在，Introspect後觸發Read-only Method或Get Property，並監看相關Signal。若資料仍不更新，再往Service Event Loop、Driver與Hardware路徑調查。

參考：D-Bus Specification；busctl Manual

2.5 / AI FOR ENGINEERING

什麼是Context Engineering？

Context Engineering是設計、選取及管理模型在每個工作階段能看到的資訊。它涵蓋指令、文件、Source、工具定義與結果、目前進度及相關歷史。

Prompt偏重「這次要做什麼、怎麼要求」；Context還要處理「需要哪些資料、何時取得、哪些已過期、目前有哪些已確認事實」。

Context內容Embedded／BMC例子管理重點
環境與版本MACHINE、Branch、Commit、BIOS／BMC版本。避免把不同Build或平台的結果混在一起。
相關證據錯誤Log前後文、Unit檔、Recipe與相關Source。保留來源、行號、時間與單位。
規範與知識官方Spec、介面Schema、專案開發規則。標示版本與適用範圍，依問題取用。
工具與觀察Build結果、Test輸出、D-Bus Introspection。記錄在哪裡執行、是否成功與是否被截斷。
任務狀態已排除假設、目前修改、待驗證項目。長任務定期更新，保留重要決策依據。

環境：平台／Firmware／Branch／Commit與部署方式。

實際：原始Response、D-Bus讀值及相關Log。
相關檔案：Unit、Service Source與API Mapping，附版本位置。

本次範圍：先定位資料在哪一層停止更新。
相關且新鮮的資料比大量無關資料更有用。可以先提供索引與摘要，再按需讀取原文；摘要要保留證據出處與未解問題。把資料放進Context，不等於更新模型的訓練權重，也不保證之後每個Session都會記得。

文件與Log是待分析的資料；其中夾帶的指令應按資料來源與任務授權處理，不能自動變成Agent的操作規則。檢索到的資料也要核對是否適用目前平台。

Harness Engineering是設計AI Agent周圍的工作環境、工具、執行流程及回饋機制，讓它能持續完成並驗證任務。這個用語仍在演進，不同實作的邊界可能不同；本教材以Coding Agent的工作系統來理解。

概念主要問題同一個Bug Fix中的例子

  1. 接收Issue與驗收條件，讀取目前Repo及環境狀態。

  3. 產生局部修改，檢查Diff並執行相關Build及測試。
  4. 依失敗輸出修正假設；遇到未具備的硬體、權限或依賴時記錄阻礙。
  5. 符合驗收後交付修改與證據；達到時間／次數上限或無法取得關鍵資訊時停止並回報。

3.1 / WHAT IS REDFISH?

什麼是Redfish？

Redfish是DMTF制定的系統管理標準，結合RESTful介面、HTTPS、JSON與標準化Schema，讓Client能以一致的資料模型查詢及管理伺服器等設備。

HTTPS：如何傳送

Client送出HTTP Request，TLS保護傳輸並驗證對端。

JSON：資料如何表示

用Property與Value描述版本、電源狀態或硬體資訊。

Schema：資料代表什麼

定義Resource的型別、Property語意、可用操作及限制。

對Embedded工程師而言，Redfish可視為Firmware對外提供的一層管理API。底層仍須有實際的Sensor、Inventory、Power與Update等功能實作；換成HTTPS並不會讓Driver或Hardware存取工作消失。

IPMI不是Redfish的必經路徑。在OpenBMC中，兩者可以使用共同的底層Service或D-Bus資料；不代表每個Redfish Request都要轉成IPMI Command。

第一個Read-only Request

以下用Bash與curl讀取Service Root。Hostname、帳號與CA檔案都要替換；Hostname需與BMC憑證相符。curl會提示輸入密碼。

BMC_HOST='bmc.example.com'
BMC_USER='your_user'
BMC_CA='/path/to/bmc-ca.pem'

curl --cacert "$BMC_CA" --user "$BMC_USER" \
  -i -H 'Accept: application/json' \
  "https://$BMC_HOST/redfish/v1/"

-i同時顯示Response Headers與Body。範例使用Basic Authentication over HTTPS；Redfish也提供Session Token機制。若使用Token，後續Request仍需帶上對應的Authentication Header。

依據：DMTF Redfish與Redfish User Guide v1.1.0。

3.2 / MOTIVATION

為什麼需要Redfish？

當管理需求從單台伺服器的Power、Sensors與SEL，擴大到大量、多廠商、複雜硬體的Inventory與Automation時，需要更容易擴充、探索及整合的標準介面。

管理需求Redfish提供的方式
看懂硬體與功能之間的關係以Systems、Chassis、Managers等Resource及Link表達資料。
減少各廠商專用資料格式的差異用標準Schema定義共同語意，並保留Oem擴充機制。
整合既有軟體工具使用HTTPS與JSON，可搭配curl、Python及各種HTTP Client。
處理耗時的管理工作以Task等機制追蹤非同步操作，並支援Event通知等管理能力。
有標準Schema不代表每台平台都實作全部功能。Client仍須確認Resource、Property、Action、Schema版本與權限；IPMI與Redfish也可能同時存在。

依據：DMTF Redfish White Paper v1.0.4。

3.3 / TRADE-OFFS

Redfish相較於IPMI的優缺點

以下比較的是常見設計取捨；實際資源用量、效能與功能覆蓋，仍須在目標平台量測及確認。

面向IPMIRedfish
操作模型以Command與二進位欄位為主。以URI、Resource與Property為主，便於描述物件關係。
資料可讀性工具會解碼；Raw資料需要對照欄位規格。JSON較容易閱讀及使用通用Parser，但Payload通常較大。
資料模型與擴充基本管理功能成熟；新增能力可能使用OEM Command。Schema涵蓋較廣的管理需求；仍可能有Oem差異與Optional功能。
工具整合ipmitool及既有維運工具普及。容易使用HTTP函式庫、JSON與Web生態工具整合。
實作成本Command本身通常精簡；也需實作驗證與平台Handler。需處理TLS、HTTP、JSON、Schema與API生命週期，增加實作及驗證工作。
資源與效能二進位Payload較精簡，適合既有簡單操作。HTTP／TLS與JSON有額外成本；可透過Session重用及資料組織降低部分負擔，需實測。
Securitylanplus支援驗證、Integrity與Encryption，仍取決於Cipher及設定。採HTTPS／TLS與標準管理機制；仍須正確處理憑證、權限及API漏洞。
既有相容性既有Host In-band與維運流程常已使用IPMI。遷移需修改Client與流程；不能假設能直接取代KCS或既有SOL。

對工程師的意義：Redfish讓API整合與資料理解更容易，同時增加Web Protocol、Data Model與Compatibility的學習及實作需求。不能只用「比較新」來判斷它在所有情境都較好。

整理依據：DMTF Redfish White Paper與本教材第四部分；效能與開發成本為依協定構成做的工程比較，非平台Benchmark結論。

3.4 / RESTFUL

什麼是RESTful？

REST（Representational State Transfer）是一種架構風格。RESTful表示介面設計遵循REST的原則。對本教材，先掌握「以Resource為中心，透過標準介面交換它的Representation」。

REST概念入門理解
Client–ServerClient負責發出需求，Server提供資料與操作能力，雙方可以分別演進。
Stateless每個Request帶足處理所需的資訊，不依賴隱含的前一步操作上下文。
Uniform Interface以一致方式識別Resource、交換Representation，並透過Link導覽。
CacheResponse應表明能否快取；即時狀態需考慮資料新鮮度。
Layered SystemClient可經由中介層與Service互動，不需知道所有內部實作。
Code-on-demand（Optional）可選擇性下載程式碼給Client執行；Redfish入門不需從這一項開始。
Stateless不等於Server不能保存資料或Authentication Session。伺服器可以有Resource狀態與Session Token；Client每次仍需送出完整的目標URI、Method、驗證資訊及必要Payload。

HTTP Method如何表達操作？

Method用途Redfish例子
GET讀取Representation查詢System的PowerState。
PATCH部分修改Resource修改平台允許寫入的AssetTag。
PUT替換Resource的表示內容只在目標Resource／Service支援時使用，不能假設所有Redfish URI都支援。
POST新增Resource或執行Action建立Session，或對Reset Action送出Request。
DELETE刪除可刪除的Resource刪除一個Session。

URL看起來像階層路徑、使用HTTP或回傳JSON，都不足以單獨證明API符合REST。還要看Resource、Method語意、Representation與Link等設計。

依據：Fielding Dissertation，第5章與RFC 9110。

3.5 / RESOURCE & REPRESENTATION

什麼是REST Resource？

Resource是API中可被識別、查詢或操作的概念對象。它可以代表一個System、一個Manager、一組Chassis，或一個Task。Resource不必是檔案，也不必一對一對應某顆硬體。

概念範例要區分的事情
Resource一個受管理的ComputerSystem被管理的對象本身。
URI/redfish/v1/Systems/system識別及定位該Resource的位址；system只是範例ID。
RepresentationGET回傳的JSON該Resource在當下的一種表示，不是Resource本身。
PropertyPowerStateResource中的資料欄位，不一定能寫入或單獨作為URI。
Collection/redfish/v1/Systems以Members連結到成員Resource。
ActionComputerSystem.Reset對Resource執行操作；應使用回應中公布的target。

讀懂一段JSON

以下是教學用節錄，不是完整Response，也不是固定平台路徑。

{
  "@odata.id": "/redfish/v1/Systems/system",
  "Id": "system",
  "Name": "Example Host",
  "PowerState": "On",
  "Status": {
    "State": "Enabled",
    "Health": "OK"
  }
}

@odata.id是此Resource的識別URI；PowerState是讀到的電源狀態。要改變電源，應查閱Resource支援的Reset Action，不能直接假設可以PATCH PowerState。

從Service Root探索

  1. GET /redfish/v1/，找到Systems、Chassis與Managers等Link。
  2. 跟隨Systems的@odata.id，讀取Collection。
  3. 從Members中的@odata.id選擇實際System，再GET其內容。
  4. 需要操作時，核對Property權限、Actions、Allowable Values與ActionInfo。
Systems描述受管理的運算系統；Chassis描述機箱等實體容納結構；Managers描述BMC等管理控制器。不要把三者視為同一個物件，也不要把範例ID硬寫成所有平台通用的路徑。

依據：DMTF Redfish User Guide v1.1.0。

3.6 / HTTP STATUS CODES

常見的HTTPS Return Code

更精確的名稱是HTTP Status Code。HTTPS是在TLS上傳送HTTP，Status Code的語意相同。TLS Handshake或憑證驗證失敗時，Client可能尚未取得任何HTTP Response。

類別入門判讀
2xx成功或已接受，仍需看是否非同步及Body內容。
3xx重新導向，讀取Location。
4xxRequest、驗證、權限或目前條件需要調整。
5xxServer或中介層無法完成處理。
Code名稱意義與下一步
200OK成功；仍檢查Body與ExtendedInfo，尤其是多Property修改的部分成功情境。
201Created已建立Resource；檢查Location及新Resource。
202Accepted已接受但尚未完成；Redfish通常以Location指向Task Monitor，需繼續追蹤。
204No Content成功且沒有Response Body；不要強制將空Body解析為JSON。
301 / 302Moved Permanently / Found永久／暫時Redirect；部分Client可能在重新導向時把POST改為GET。
307 / 308Temporary / Permanent Redirect保留Method的Redirect；依Location處理，留意Host與驗證資訊。
400Bad RequestRequest有問題；檢查JSON、Property、型別及參數。
401Unauthorized缺少有效Authentication；檢查密碼、Token與是否過期。
403ForbiddenServer拒絕此Request；常見原因是Privilege不足。
404Not Found找不到目標Resource；確認URI、ID及平台支援情況。
405Method Not Allowed目標Resource不允許該Method；查看Allow Header。
409Conflict操作與目前Resource狀態衝突；檢查前置條件與錯誤訊息。
412Precondition Failed條件式Request未成立，例如If-Match與目前ETag不符。
415Unsupported Media TypeRequest內容格式不支援；檢查Content-Type。
429Too Many Requests觸發Rate Limit；若有Retry-After，依它及重試策略降低請求頻率。
500Internal Server ErrorServer內部錯誤；保存Request、Response與BMC Log。
501Not ImplementedServer未實作所需功能，例如不認得或未支援的Method。
503Service Unavailable暫時無法服務；確認初始化、維護或負載狀態，以及Retry-After。

讀Response的順序

  1. Status Code：先分辨成功、非同步、Redirect或錯誤。
  2. Headers：看Content-Type、Location、ETag、Allow或Retry-After。
  3. Body：看實際Resource，或錯誤回應中的error、@Message.ExtendedInfo與MessageId等細節。
  4. 讀回／追蹤：修改後確認實際值；非同步操作追蹤到最終結果。
Status Code不是Firmware內部錯誤碼或IPMI Completion Code。只看到500不能直接推論是Driver錯誤；只看到200，也不能略過Response內容。

依據：RFC 9110、RFC 6585及DMTF DSP0266 v1.25.0。

3.7 / IDEMPOTENCY & RETRY

什麼是Idempotency？

Idempotency（冪等性）是指：相同Request執行一次或多次，對Server產生的預期效果相同。它不要求每次Response Body或Status Code完全相同。

設定值：設成Lab-A

重複設定同一個固定值，通常不會累積新的效果。

操作：增加一次

每做一次就再增加，不能視為相同效果。

觸發：重新開機

重複送出可能再次觸發Reset，不可盲目重試。

Safe與Idempotent是兩件事

Safe：Client沒有要求變更Server狀態，例如GET。Idempotent：允許變更狀態，但重複相同操作的預期效果不會持續累積，例如DELETE。

MethodHTTP的一般語意Redfish／面試理解重點
GET / HEADSafe且Idempotent。重複查詢不要求改變資源，但Sensor值仍可能隨時間變化。
PUTIdempotent，非Safe。以相同內容替換；需先確認Service是否支援。
DELETEIdempotent，非Safe。第一次刪除後，第二次可回404；目標仍維持已刪除。
POST不保證Idempotent，非Safe。重複建立Resource或觸發Action可能產生額外效果。
PATCH一般HTTP不保證Idempotent，非Safe；取決於修改語意。Redfish規範建議：無外部變更時PATCH應具Idempotency，但ETag可能已不同。

Redfish例子：固定設定一個Property

假設平台允許修改此Chassis的AssetTag，以下只表示Request語意。URI是範例；實作前需先Discovery並確認權限。

PATCH /redfish/v1/Chassis/chassis
Content-Type: application/json

{"AssetTag":"Lab-A"}

在沒有外部變更的前提下，送一次或多次的預期結果都是AssetTag = Lab-A。但是，若第一次Request已更新ETag，再用舊If-Match重送，可能收到412；這不等於Property設定不是Idempotent。

為什麼Embedded工程師需要理解？

Network Timeout只代表Client未取得結果，不代表Server沒有執行。若對Reset Action自動重送POST，可能再次觸發Reset；若是建立Resource，則可能重複建立。

  1. 先確認Method與操作的語意，不能所有Timeout都套用相同Retry。
  2. 若已拿到Task Monitor或新Resource的Location，優先查詢它。
  3. 若修改結果不確定，先讀回Resource，核對預期值與目前狀態。
  4. 若使用ETag／If-Match，衝突後重新讀取並評估，避免覆蓋別人的變更。
讀完後，試著回答
  • 為什麼GET兩次讀到不同溫度，仍可具有Idempotency？
  • 收到202後，為什麼不能直接宣告Firmware Update成功？
  • DELETE第一次回204、第二次回404，是否違反Idempotency？
  • POST Reset後Timeout，你會先收集什麼資訊，再決定是否重試？

依據：RFC 9110 §9.2.2、RFC 5789與DMTF DSP0266 v1.25.0 §7.6–7.11。

3.8 / SCHEMA BASICS

什麼是Schema？

Schema是資料模型的定義與約定。在Redfish中，它描述Resource有哪些Property、資料型別及語意、可用Action，以及相關限制，讓Client與Service對同一份資料有共同理解。

如果你熟悉C／C++，可以先把Schema類比成「型別宣告加上介面規格」：它不只列出欄位，還說明欄位的用途、有效值與操作規則。不過Schema不是記憶體Layout，也不是BMC的Driver實作。

概念Embedded類比Redfish例子
Schema型別與介面定義Manager的資料模型。
Resource一個可識別的物件平台上的某個BMC Manager。
Payload一次序列化後的物件資料GET該Manager時回傳的JSON。
Service Implementation實際執行邏輯取得Firmware Version，再產生符合Schema的Response。

Schema與JSON Payload有什麼不同？

以下是Manager Resource的教學用節錄；URI與版本值是範例。

{
  "@odata.type": "#Manager.v1_17_0.Manager",
  "@odata.id": "/redfish/v1/Managers/bmc",
  "Id": "bmc",
  "Name": "Example BMC",
  "FirmwareVersion": "1.2.3"
}

@odata.type宣告此Resource使用的型別與Schema版本。Manager.v1_17_0.Manager表示Manager Namespace中的對應版本與型別，不是BMC Firmware版本，也不是Redfish Protocol版本；Firmware版本則在FirmwareVersion。

常見Schema表示格式

DMTF提供CSDL（Common Schema Definition Language，常見為XML）與JSON Schema等機器可讀格式，並提供便於閱讀的Data Model文件。兩者都在描述資料模型；不能因為Response是JSON，就認為驗證工具一定使用JSON Schema。

Schema定義「應如何表示資料」；Payload是「這次實際回傳的資料」。JSON語法正確只代表可以解析，不代表符合Schema或符合真實硬體狀態。

依據：DMTF DSP0266、Manager v1.17.0 JSON Schema。

3.9 / READING A SCHEMA

Schema定義了哪些東西？

定義內容你可以從中知道什麼常見欄位／概念
Resource與型別這是哪種Resource、繼承或參照哪些型別。Namespace、Type、Version、Reference。
Property與語意欄位名稱、大小寫與代表的意義。properties、description、longDescription。
資料型別與結構是string、boolean、integer、number、object或array。type、items、$ref。
是否可為null欄位出現時，是否允許沒有可用值。Nullable或包含null的型別定義。
必需欄位Service必須提供哪些Property，建立時Client必須送哪些欄位。Required與RequiredOnCreate是不同要求。
讀寫規則Property是Read-only、Read-write或Write-only。Permissions；JSON Schema中的readonly、writeOnly。
有效值與範圍Enum、數值上下限、字串格式及單位。enum、minimum、maximum、pattern、units。
Resource關係哪些Property連結到其他Resource或Collection。Reference、Link與URI Pattern。
Action與參數可定義哪些Action、參數型別與要求。Actions、Parameters、RequiredParameter。
版本與演進Property或Enum從哪個版本加入、何時Deprecated。versionAdded、versionDeprecated等Annotation。

實際讀一個Property定義

以下節錄Manager v1.17.0中FirmwareVersion的型別與讀寫限制：

"FirmwareVersion": {
  "readonly": true,
  "type": ["string", "null"]
}

因此"FirmwareVersion": "1.2.3"的型別符合此定義；"FirmwareVersion": 123則不符合。即使它是合法JSON，也不能把number當成string。readonly: true表示Client不能用PATCH直接修改此欄位。

三個容易混淆的地方：
  • 允許null不等於允許缺少Property；是否必需出現要另外看Required。
  • Schema允許Read-write，不代表每個平台都一定可寫，也不代表每個帳號都有權限。
  • Schema列出完整Enum或Action，不代表平台支援全部；還需看實際Capability、Allowable Values及ActionInfo。

Schema、Protocol Specification與Privilege／Interop Profile要一起理解。Schema本身不會規定Firmware內部怎麼讀I²C，也不能保證平台具備所有Optional功能。

面試前的閱讀練習

拿到一份陌生Resource時，先找@odata.type，再核對對應版本的Schema。選三個Property，說明它們的型別、語意、是否可寫及是否允許null；最後說明如何用實際Response確認平台支援範圍。

依據：DMTF DSP0266的Schema Annotation章節與Manager v1.17.0。表中的名稱可能依CSDL與JSON Schema格式而不同。

3.10 / REDFISH SERVICE VALIDATOR

什麼是Redfish Service Validator？

Redfish Service Validator是DMTF提供的開源Python工具，主要透過GET取得Resource Response，依Redfish CSDL Schema檢查資料模型的一致性。

可以把它理解成自動化的「介面資料檢查員」：找出Resource，再核對宣告的型別與Property。它不需要知道底層Firmware如何取得資料。

常見檢查可能發現的問題
Resource存取與JSONGET失敗、Response不是可解析的JSON Object。
Schema與版本@odata.type有誤，或找不到對應Schema。
Property結構與型別缺少Required Property，或用number回傳string欄位。
值與限制Enum大小寫錯誤、數值超出範圍或格式不符。
Link與Action宣告Resource參照異常，或Action不屬於宣告的Resource型別。
Validator Pass的範圍要看清楚。它不能證明Sensor讀值符合實際硬體，也不代表POST／PATCH／DELETE、Reset、Firmware Update或Security測試全部通過。Resource資料檢查以GET為範圍；Session Authentication本身仍可能涉及建立與刪除Session。

如何開始使用？

以下是閱讀與操作範例，不要求面試者事前有可連線的BMC。先依官方README安裝工具與Dependencies，再使用該版本提供的Configuration Template設定目標及驗證資訊。

# 取得工具並安裝到獨立的Python環境
 git clone https://github.com/DMTF/Redfish-Service-Validator.git
 cd Redfish-Service-Validator
 python3 -m venv .venv
 . .venv/bin/activate
 python -m pip install -r requirements.txt

# 查看目前版本的參數
 python RedfishServiceValidator.py --help

# 將官方Configuration Template另存為validator.ini並完成設定後：
# 只檢查Service Root
 python RedfishServiceValidator.py --config ./validator.ini \
   --payload Single /redfish/v1/ --logdir ./logs-single

# 從Service Root探索Resource Tree
 python RedfishServiceValidator.py --config ./validator.ini \
   --payload Tree /redfish/v1/ --logdir ./logs-tree

實際執行前需設定Service URL、帳號及Authentication方式，並備妥對應Schema或讓工具可取得Schema。含密碼的Configuration檔只保存在受控環境，不要放進共用教材或Git。

看到Fail，怎麼調查？

  1. 先定位失敗的URI、Property、Error與預期型別。
  2. 保存該次GET的Headers及JSON，核對@odata.type與Schema版本。
  3. 區分Service資料錯誤，或Network、Authentication、Schema下載／版本等測試環境問題。
  4. 若是資料錯誤，再往API Mapping、D-Bus、Driver或Hardware追查；修改後先重測Single，再擴大到Tree。

報告需連同工具版本、Schema、測試範圍、帳號權限及跳過項目一起看。只測Single或限制Collection數量，就不能把結果描述成所有Resource都驗證完成。

  • FirmwareVersion回傳number時，應先修資料型別，還是先改Schema宣告？為什麼？
  • Validator Pass，是否能證明Reset Action真的會讓Host重新開機？還需要什麼測試？

C／C++與Debug閱讀Service程式、分析Log與追蹤錯誤回傳以證據建立假設，再用實驗縮小範圍

Host、BMC、IPMI與ipmitool

Host是執行主要工作負載的伺服器系統，包含CPU、BIOS與Host OS。BMC則是獨立的管理控制器，具有自己的Firmware與管理功能；在Standby Power仍供電的設計下，Host關機後BMC仍可運作。實際可讀取的資訊，仍取決於平台與電源狀態。

BMC（Baseboard Management Controller）是伺服器上的管理控制器；IPMI（Intelligent Platform Management Interface）是一套管理介面規範；ipmitool則是操作IPMI的Command-line Tool。

Access

建立管理連線，讀取BMC識別資料。

Monitoring

查看Sensors、FRU與SEL，了解平台狀態。

Control

控制Host電源，透過SOL存取Serial Console。

連線方式操作位置常見介面前提
Out-of-band管理用電腦IPMI over LAN / lanplusBMC網路可達、IPMI LAN已啟用、帳號有權限
In-band受測伺服器的Host OSSystem Interface / open，常見底層為KCSHost可執行工具，且有可用的IPMI Driver與Device Node
IPMI、Redfish與Web UI是不同的管理介面。第三部分介紹Redfish與REST概念，第四部分補充IPMI；不需要先有Web開發經驗。OpenBMC是一套BMC Firmware實作，IPMI則是它可提供的管理介面之一。
4.2 / FIRST CONNECTION

建立第一個IPMI連線

以下範例在管理端Linux的Bash執行，請先安裝ipmitool。IP與帳號均為範例，請改成受測平台的資料；密碼由終端機提示輸入。

# 確認工具版本
ipmitool -V

# 設定受測平台，請替換成實際資料
BMC_IP='192.0.2.10'
BMC_USER='your_user'

# Bash Function：後續範例統一使用 ipmi
ipmi() {
  ipmitool -I lanplus -C 17 -H "$BMC_IP" -U "$BMC_USER" -a "$@"
}

# 第一個Read-only測試
ipmi mc info
參數用途
-I lanplus使用IPMI v2.0的LAN介面。
-C 17指定Cipher Suite 17，需由Client與BMC共同支援。
-H / -UBMC IP或Hostname，以及登入帳號。
-a互動式輸入密碼；這裡每次呼叫ipmi都會提示輸入。
mc info讀取BMC Device與Firmware識別資訊。
如何判讀？

確認指令成功回應，並比對Firmware Revision、Manufacturer ID與Product ID是否符合受測平台。mc info不等於完整的Component Version Inventory，也不能用它直接取得所有BIOS、NIC或GPU版本。

在Host OS使用In-band

# 在受測Host OS執行，並確認IPMI Driver已就緒
sudo ipmitool -I open mc info

若遠端Session建立失敗，先檢查IPMI LAN設定、帳號權限、UDP 623與Cipher支援。不要直接假設所有平台都有相同設定。

4.3 / MONITORING

讀取Sensors、FRU與SEL

這三類資料分別回答：「目前狀態如何？」「裝的是什麼？」「之前發生什麼？」

先理解資料從哪裡來

以常見OpenBMC Sensor實作為例，Hardware Driver可透過hwmon／sysfs提供讀值，User-space Sensor Service再將資料提供到D-Bus，供IPMI等管理介面使用。不同Sensor來源與平台可能採用不同路徑。

觀察層次你要問的問題
Hardware／Driver裝置是否存在？Driver是否成功讀到資料？
Sensor Service／D-Bus資料是否更新？Value、Unit與Availability是否合理？
IPMI／ClientSensor對應與編碼是否正確？Client顯示值是否一致？

D-Bus是Linux上的IPC機制。這裡先理解它負責Service之間傳遞資料即可，不要求先記住OpenBMC的Service名稱。

4.3.1 Sensors與SDR Read-only

SDR（Sensor Data Record）提供Sensor的描述與相關設定；Sensor Reading則反映目前讀值或Discrete State。

ipmi sdr elist
ipmi sensor list

# 先從清單取得實際Sensor名稱，再替換下列範例
ipmi sensor get "CPU Temp"

觀察重點：依平台Sensor List核對名稱、數量、單位與狀態。Host關機、元件未安裝或平台條件未滿足時，部分讀值可能為na；需先理解平台條件，才能判斷是否異常。

4.3.2 FRU Read-only

FRU（Field Replaceable Unit）資訊可包含Board或Product的識別資料。

ipmi fru print

觀察重點：對照實際硬體的Part Number、Serial Number與Manufacturer；空白欄位是否允許，依平台規格判定。

4.3.3 SEL Read-only

SEL（System Event Log）記錄平台事件；應比較測試前後的差異。

ipmi sel info
ipmi sel elist

# 以清單中實際的Record ID查閱細節；0x0001只是範例
ipmi sel get 0x0001

觀察重點：確認事件內容、時間與測試動作相符；檢查是否新增未預期的錯誤事件。事件名稱與OEM解碼可能因平台而異。

實作順序：先保存測試前的Sensors／SEL，再執行測試動作，最後讀回比對。保留既有SEL，才能追查事件的前後關係。
4.4 / CONTROL

Power Control與Serial over LAN

4.4.1 Host Power Control 會影響Host運作

先讀取狀態，再選擇單一測試動作。Power Off、Reset與Cycle會中斷Host工作，請在已安排的測試時段執行。

# 查詢Host電源狀態
ipmi chassis power status
指令（每次選一項）操作目的驗證重點
ipmi chassis power on開啟Host電源Power Status與實際開機狀態一致
ipmi chassis power off強制關閉Host電源確認Host關機，並保存相關事件
ipmi chassis power soft要求Soft Shutdown需Host OS支援並正確處理
ipmi chassis power resetHost Hard Reset確認Host重新開始Boot
ipmi chassis power cycleHost關電後再開電確認電源轉換及Boot完成
Power Cycle ≠ AC Cycle。Host Power Cycle通常不會移除BMC的Standby Power。AC Cycle必須透過受控PDU或實體斷電，再恢復供電；等待時間與開機預期依平台測試程序設定。

4.4.2 SOL Serial over LAN

SOL透過網路傳送Serial Console。BMC需支援並啟用SOL，Host端的BIOS／OS也需正確設定Console Redirection及Baud Rate。

# LAN Channel編號需依平台確認；此處以1為例
ipmi sol info 1

# 建立互動式Serial Console
ipmi sol activate

觀察重點：能看到預期Console輸出，且可正常輸入。結束時，在新的一行輸入~.離開；若透過SSH使用，需留意SSH自己的Escape Character處理。

若已顯示SOL Session啟用，但沒有Console文字，先確認Host狀態與Serial設定，不能只憑空白畫面判斷BMC故障。

4.5 / RECOVERY & UPDATES

區分BMC Reset、Host Reset與Firmware Update

BMC Reboot 管理連線會暫時中斷

# 僅在平台支援且已安排測試時執行
ipmi mc reset cold

# 等待平台定義的BMC恢復時間，再重新驗證
ipmi mc info
ipmi sensor list
ipmi chassis power status
ipmi sel elist

確認BMC恢復後可重新登入，Sensors在預期時間內恢復，Host狀態與設定符合平台要求。請先分清楚三個動作影響的範圍：BMC Reboot重啟管理控制器、Host Power Cycle改變Host電源、AC Cycle移除並恢復平台供電。它們不能互相代替。

BMC／BIOS Upgrade與Downgrade

沒有適用所有BMC平台的通用Firmware Update指令。依平台支援的Redfish UpdateService、Web UI或Vendor Tool操作；不可將特定OEM Raw Command當成通用流程。
  1. 記錄Platform／SKU、目前版本、目標Image與設定保留選項。
  2. 依平台程序執行Update，確認Image相容性與Downgrade／Anti-rollback限制。
  3. 完成必要的Reboot或Power Cycle後，確認實際啟用版本。
  4. 確認更新後仍能連線、讀取Sensors與控制Host，並檢查相關錯誤Log。

BIOS及其他Component Version應透過平台支援的Inventory或版本查詢方式確認；不要只依賴mc info。

4.6 / TROUBLESHOOTING

把既有Debug經驗帶進BMC

面對陌生平台時，先確認「在哪一層出問題」，再決定下一個實驗。記錄操作條件、預期結果與實際結果，讓每一步都有可驗證的目的。

練習情境：Host關機後，一個CPU相關Sensor顯示na。先確認該Sensor在Host關機時是否應有資料，再比較Host開機後的結果；若仍異常，才逐層檢查Sensor Service與底層資料來源。
無法建立LANplus Session

先確認BMC IP與路由、管理網路及UDP 623，再核對IPMI LAN是否啟用、帳號密碼、Privilege與Cipher Suite支援。Ping成功只代表部分網路可達，並不代表IPMI服務正常。

Sensor顯示na或數量不同

比對Platform／SKU、元件Presence、Host電源狀態及BMC初始化時間。記錄實際Sensor名稱與預期；若相同硬體、Firmware與電源條件下仍有差異，再追查Sensor Provider、SDR與硬體讀取路徑。

Power指令回應成功，但Host沒有完成Boot

指令被接受不等於Host已完成開機。讀回Power Status，搭配SOL、POST狀態及SEL，區分Power Sequence與BIOS／OS階段的問題。

SOL可以啟用，但畫面空白

確認Host是否正在輸出Serial資料、BIOS／OS Console Redirection、Baud Rate及SOL權限。必要時依平台程序檢查是否有既存Session。

  1. Host關機後，BMC為什麼仍可能回應IPMI？需要哪些供電與網路條件？
  2. In-band與Out-of-band的Request從哪裡送出？各自需要什麼條件？
  3. Sensor數值異常時，你會收集哪些資料，如何區分Driver、Service與介面問題？
  4. SOL有連線卻沒有文字，與Serial Console除錯有哪些相同之處？
  5. 選一個過去的Embedded Debug案例，說明你如何建立假設、設計實驗與確認原因。
